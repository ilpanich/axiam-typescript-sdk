    • ssfStreamInputWith(
          stream: SsfStream,
          changes?: Partial<SsfStreamInput>,
      ): SsfStreamInput

      The change-taking read-modify-write form for ssf.updateStream (contract 1.62, §32.2): (stream, changes) → SsfStreamInput.

      It applies changes over what was read and returns the replacement body:

      • events_requested and expected_updated_at are sent as read — an [] stays [], and the timestamp is the stream's own updated_at string, byte for byte, never re-rendered — so the replacement lands only on the version you read (a write made since, the receiver's included, is 409: reload, then retry) and a receiver's narrowing is not widened.
      • When changes names events_allowed and not events_requested, events_requested is cut to the new events_allowed: the entries of the read list that are in the new ceiling, in their order. An events_requested named in changes is sent as given — the server judges it (400 outside events_allowed).

      The three meanings of events_requested on an update still hold for what you name: absent resets the stream to every event of events_allowed, [] is stored as the receiver's "none", a list is stored as given. To reset deliberately, name events_requested: null — the key is then left out of the body. Likewise expected_updated_at: null is "none": the key is left out and the replacement is conditional only on the version the server reads during the request. A member of changes whose value is undefined is not a change.

      authorization_header and clear_authorization_header are left absent unless changes names them (absent keeps the stored header, §32.3 rule 5).
